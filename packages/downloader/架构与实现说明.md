# Downloader 插件 —— 设计与实现说明

> 一个集成在 DSH 侧栏里的 **蓝牙芯片烧录工作台**。
> 驱动官方 Downloader 引擎完成烧录，同时自带 1.5 Mbps 串口日志，两者自动互斥切换。
>
> 版本 0.1.0 · 已验证平台 Windows 10/11 · DSH 桌面 0.2.1-rc.3

---

## 一、它解决什么问题

原来的工作流要在三个窗口之间跳：

```
VS Code 改代码 → 编译 → 切到 Downloader 点下载 → 切到串口助手看日志
```

痛点：

| 痛点 | 后果 |
|---|---|
| 烧录和看日志用同一个 COM | 开串口就烧不了，烧完又得手动把串口"抢"回来 |
| Downloader 界面操作繁琐 | 每次烧录要选文件、点按钮 |
| 日志分散 | 烧录日志在 Downloader，板卡日志在串口助手，出问题要对照两个窗口 |
| 想让编译完自动烧 | Downloader 自带的 AutoStart 需要手动点一次激活，且一旦关闭就断了 |

**本插件把这四件事合并成一个侧栏页面**，并自动处理串口互斥。

### 为什么用两个 helper 子进程

| 原因 | 说明 |
|---|---|
| **位数不同** | Downloader 是 x86，`WM_COPYDATA` 需要同位数进程才能拿到正确句柄结构；串口用 64 位能直接跑 1.5 Mbps 大缓冲 |
| **崩溃隔离** | 串口 helper 崩了不影响烧录，反之亦然 |
| **职责单一** | 一个只管字节流，一个只管窗口消息 |

两者都是**零依赖编译**（只用 .NET Framework 自带类库），不需要装任何运行时。

## 三、核心机制

### 3.1 串口与烧录的互斥

Windows 的 COM 口是**独占**的：同一时刻只能一个进程持有。

实测确认的三条事实：

1. Downloader **空闲时不占用 COM**（可以被别的程序打开）
2. Downloader **烧录期间会独占 COM**
3. Downloader **烧完仍持有 COM** 去监控设备

因此不能两边同时抢。本插件的策略是**分时复用**：

```
用户开串口看日志         工作台持有 COM22
        ↓ 点「连接」
连接 Downloader          工作台让出 COM22  ──► Downloader 才能扫到设备
        ↓ 点「烧录」
烧录中                   Downloader 独占
        ↓ 烧录完成
抢回串口                 让 Downloader 退出 ──► 立即 open，空窗 ~8ms
```

关键实现点：

```js
// 让出串口前先记住"用户想要串口"，烧完按这个意图还回去
state.serial.resumeAfterFlash = state.serial.wantOpen
  || { port: state.serial.port, baud: state.serial.baud }
await serialHelper.command('close', {})
```

**空窗 8ms 是怎么做到的**（这是踩过坑的地方）：

| 早期实现 | 问题 | 修正 |
|---|---|---|
| `open` 超时设 1500ms | 失败时阻塞 1.5 秒，重试变成"每 1.5 秒一次" | 降到 600ms |
| 每次重试前杀 helper 重建 | .NET 冷启动 1.0~1.4 秒 | 复用存活 helper，只在死掉时重建 |
| 固定 `sleep(1200)` 等进程退 | 白等 | 改成 50ms 轮询，一可用就接上 |

结果：板卡重启后的 `Hello Platform` / `sram total` 等启动日志能完整保留。

### 3.2 烧录：驱动官方引擎而非重造

**没有逆向烧录协议**。原因：

- 协议藏在 .NET Reactor 加壳的 `Downloader.exe` 里，逆向成本 3~6 周且有变砖风险
- 官方引擎已经稳定，只需要控制它

做法是用 `WM_COPYDATA` 给 Downloader 发命令，读它的响应：

```
DownloaderIpcBridge.exe --exe <Downloader.exe> --args "BackShowMode {hwnd}" --no-hide
```

消息格式（实测还原）：

```
命令下行：  纯文本，如 download / readinfo / erase
状态上行：  DownSta|COM|进度0..10000|状态|MAC
           FileInfo|<dcf路径>|watch||<大小>|<校验码>
           DevChange|1|COM22
           Error|Download Start Fail
```

一次成功烧录的完整状态序列：

```
等待中 → 扫描中 → 初始化 → 就绪 → 预校验 → 下载中 → 校验中 → 等待中 → 完成
```

**⚠️ 两个必须处理的坑**

**坑 1：`Download Start Fail` 是静默失败**

在「扫描中」阶段发 `StartDownload`，Downloader 会**静默丢弃**，日志只写一行「扫描中」然后永远不动。

对策：发命令后 3 秒无进展就重试，最多 3 次。

**坑 2：`COMEnable=False` 时它根本不扫串口**

`Downloader.config` 里这个键是"能不能扫串口"的总闸：

```xml
<add key="COMEnable" value="False" />   ← 表现为"一直连不上、必须手动点它的串口按钮"
```

对策：每次连接前检查并自动改成 `true`（改前备份，只动这一个键）。

### 3.3 自动烧录（编译完自动烧）

需求是"编译完自动烧"。官方 `AutoStart` 有两个局限：

- 需要在 Downloader GUI 里**手动点一次**才激活
- 本插件为了还串口会关掉 Downloader，一关就断

所以**工作台自己做监听**：

```
每 700ms 检查 dcf 的 mtime + size
        ↓ 变了（= 编译完成）
等 1.2 秒让它写完
        ↓
串口开着？→ 先让出
Downloader 关了？→ 重新拉起（含 COMEnable 校正）
        ↓
等设备在线 → 烧录 → 自动重试 → 烧完还串口
```

**dcf 路径怎么来**：不用扫盘猜，直接读 Downloader 界面里的下拉框。

实测发现：用户在 Downloader 里切 dcf 时，它**既不推 `FileInfo`、也不写 config**，那个选择只存在它内存里。但它是 WinForms 程序，dcf 选择是标准 `COMBOBOX` 控件，可以用 Win32 消息读：

```csharp
CB_GETCURSEL  → 当前选中索引
CB_GETLBTEXT  → 该索引对应的路径
```

封装成 helper 的 `curdcf` 命令，插件每 3 秒查一次，变了就自动跟随。

### 3.4 日志系统

**为什么原来的日志"无缘无故换行"** —— 三层叠加：

```
① helper: p.Read(64KB) 一次读到什么就发什么 → 一行常被切成 2~3 片
② host:   每片当一条日志 pushLog()
③ 前端:   white-space: pre-wrap → 又把残留的 \r\n 渲染成换行
```

修法（两层都改）：

- **host 按行聚合**：维护行缓冲，遇 `\n` 才落一条；半行超 250ms 强制派发（防卡住）
- **前端改 `white-space: pre`**：不再二次换行

**容量设计**（为 AI 阅读而设）：

| 项 | 值 |
|---|---|
| Host 缓冲 | 50,000 条（约几百次烧录，≈3.6 MB） |
| 前端内存 | 20,000 条 |
| 单次查询上限 | 5,000 条，可翻页 |
| 写入 6 万条 | 41ms（早期实现 2.7 秒） |
| 全量搜索 5 万条 | 4ms |

写入优化：早期每条都 `splice(0, n)` 会反复搬整个数组，改成溢出 2000 条才批量剪一次。

**日志来源标记**：

| 标记 | 来源 |
|---|---|
| `B` | 板卡串口输出 |
| `D` | 烧录日志（Downloader 控制台） |
| `S` | 系统/状态 |
| `U` | 用户发送 |
| `M` | 模型发送 |

## 四、接口

### 4.1 HTTP（前缀 `/downloader`）

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/events` | SSE 推流（唯一实时通道） |
| GET | `/state` | 全量状态快照 |
| GET | `/serial/list` | 枚举串口（带设备描述） |
| POST | `/serial/open` / `close` / `write` | 串口控制 |
| POST | `/flash/start` | 连接 Downloader（自动让出串口） |
| POST | `/flash/download` | 开始烧录 |
| POST | `/flash/stop` | 断开 |
| GET | `/flash/status` | 烧录状态（含进度/MAC/扫码卡住秒数） |
| GET | `/flash/diagnose` | 环境自检 |
| POST | `/flash/fix-comenable` | 一键修 COMEnable |
| GET/POST | `/watch` | 自动烧录开关 |
| POST | `/watch/path` | 指定监听文件 |
| GET | `/log/recent` | 日志检索（分页/过滤/搜索） |

`/log/recent` 的检索能力：

```
?tail=500              最后 500 条（默认）
?offset=0&limit=200    分页
?src=B,D               只看板卡/烧录
?q=Error               关键词搜索
?since=<毫秒>          某时间之后
```

响应总带 `total`，方便知道还有多少没取。

`hello` `state` `log` `log-clear` `serial` `serial-state` `flash` `watch` `project` `root`

| 工具 | 用途 |

```powershell

#    dependencies 加 "dsh-downloader": "file:<repo>/packages/downloader"
cd $env:USERPROFILE\.dsh\profiles\desktop
pnpm install

# 2) 配置本机路径
[Environment]::SetEnvironmentVariable('DSH_DOWNLOADER_DIR', '<Downloader 安装目录>', 'User')
[Environment]::SetEnvironmentVariable('DSH_DOWNLOADER_WORKSPACE', '<SDK 工程根目录>', 'User')
```

## 八、已知限制

| 限制 | 说明 | 影响 |
|---|---|---|
| `BackShowMode` 是未公开参数 | 只在 Downloader v3.6.0 验证过 | 升级官方工具需重测启动参数 |
| 串口与烧录互斥 | Windows COM 独占，无法真正并行 | 连接时会短暂让出串口 |
| 蓝牙虚拟串口不能烧录 | COM3/COM4 是 BthModem，`Tx` 返回 0 且不报错 | 下拉框带设备名便于分辨 |
| `COMEnable` 会被 Downloader 改写 | 插件每次自动校正 | 若想用 GUI 关掉会冲突 |
| 自动跟随依赖读窗口控件 | 若官方换 UI 框架会失效 | 届时需改用文件监听等其他方案 |
| 烧录协议不自主 | 用的是官方引擎 IPC | 换工具版本需重测消息格式 |
| 板子休眠窗口窄 | 实测烧完约 10 秒后进入 `sfunc_sleep` | 自动烧录时机太晚时会失败（已在日志明确提示） |

## 九、做完这个插件学到的

按"会踩第二次"的程度排序：

1. **能读状态就先别猜**。dcf 路径我一开始靠扫盘取最新 mtime，错得离谱；最后发现直接读 Downloader 的下拉框最准。
2. **超时参数会反噬**。`open` 超时 1500ms 让"60ms 轮询"实际变成 1.5 秒一次，日志空窗因此 1578ms 而非 8ms。
3. **Web 侧和 Host 侧的作用域要分清**。`handleHttp` 是模块级函数，拿不到 `apply()` 里的闭包变量——这个错犯了三次（`ipcExe`、`ensureComEnable`、`setWatch`），每次都是 `xxx is not defined`。
4. **同一帧会重复推送**。`DownSta 完成` 一次烧录能收到 9 次，不去重会导致串口恢复被反复触发。
5. **别用 Python 批量改 JS 源码**。转义、缩进、行号漂移会连环出错，中途还把文件写过 0 字节。用 `edit` 工具做精确替换更稳。
